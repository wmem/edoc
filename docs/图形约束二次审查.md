## 为什么有的线好，有的线乱

当前有两套路由分支，见 [routing.ts](../packages/render-graph/routing.ts)：

- 普通无固定位置、无父子框的视图使用 ELK 的自动端点/路径/标签，设有边间距及不合并独立边等选项。逐端口的平行连接通常较规整。
- 带固定位置、层级框或模块内回路的视图使用 fixedRoutes 回退。无真实端口时，terminal 总是在框边中心挂接；同侧多关系缺少独立锚点分配。MAC 图同时含 positions 和 parentId，走的是这一分支。
- 回退的 orthogonal 代价目前包含长度、弯折和共线长度惩罚；共线只是软代价，没有禁止独立关系共线，也没有完整的交叉、贴线、拐点接触和容器边界通道约束。
- 父容器只将顶部 42 单位视为障碍，允许连线进入其内部；尚未为跨边界关系分配穿越位置和文字避让区。对子框的 35 单位包围留白配合 28 单位出线 stub，只留下很窄的贴边通道。
- 多端点自动布局新增零尺寸的虚拟 hub，逐个端点连接到它；最后仅在 hub 画一个圆点。代码没有对合并后的实际路径求真实分叉点，也没有对多端点树的主干/支路做整体优化。
- 当前先排一条线和标题，再排下一条，先放置的标题可能迫使后续关系绕路；缺少全图协调与最后的路径整理。

因此，layout.direction 或 routing: orthogonal 只指定部分布局策略，不能等同于完整的架构图或接线图绘制规范。

## 已有验收的盲区

原有测试验证端点保留、真实 Port/框边挂接、实体框避障、标签重叠、标签落在对应线上、静态/动态几何一致性及离线交互。自动扇出测试还检查了独立出线位置，但没有把相同规则应用到固定/层级回退场景。

当前没有覆盖：独立关系共用无端口锚点、不同关系非终端接触/长距离共线、标签覆盖容器边框，以及画出的分叉圆点是否位于实际线段联合图的 degree>=3 位置。因而此前“178 项回归通过”和“未检出既有几何缺陷”不能推导这两张图的布线质量达标。

这些缺口属于实现与验收不足。原设计已有“连接可追踪、标签可读、无误导性连线”的要求，不能把它们降为单纯美观问题，见[需求与设计基线](需求与设计基线.md)。

## 建议的下一轮规则

### 架构图

1. 无真实端口的模块为每条独立关系分配可区分的布局锚点，明确进出边与间距；这些是显示位置，不写成新的工程 Port。真实 Port 仍精确挂接，离开共享真实端点后也应保持可辨识。
2. 独立关系不靠长距离共线节省空间；只有显式聚合才可共用显示主干。交叉避免落在拐点/终端附近，不能形成看起来已接通的假分叉。
3. 视图可明确主通路，其他控制/反馈关系分配独立通道；普通方向和类别不会自动证明哪条是主通路。先解决出线和通道，再优化线长与弯折。
4. 父容器增加合理的内部布线留白和边界穿越通道；子节点关系可合法跨边界，但标题与分叉不能压在框线上。
5. 保留线上标题要求，把标签空间纳入路径与通道协调，不靠无约束的绕远解决标签冲突。

### 多端点接线图

1. 每条原关系形成一个可追溯的渲染树，保留全部真实端点。共享段只绘制一次，先明确实际树，再按实际分叉绘制标记。
2. 圆点必须对应实际分叉，不能继续仅依赖布局器的虚拟 hub；多端点树可能有多个真实 T 点。
3. 优先形成简洁主干与短支路。必要时由视图指定主干端点/主关系，而不是从“测试连接器”名称或 passive 方向猜测其地位；源 Net 的端点和电气含义不变。
4. 独立 Net 保持间距；同一 Net 的分支共线须规范化，避免重复虚线或错误的分叉提示。

项目只需提供必要的层级、方向和主通路偏好，不应为每条线维护折点坐标。主干提示若需新增公开字段，应单独明确 Schema 与兼容约定；本轮没有把这些提议写成已支持 API。

用户提出的输入属性方向与默认规则的分工，另见[布局意图输入设计](布局意图输入设计.md)；其中新增属性仍为讨论中的候选字段。

## 建议实施和验收顺序

先将这两张图作为专项失败样例，再统一自动路由与回退的约束：

1. 修复固定/层级图的独立锚点、共线和非终端接触；复验标题与父框边界。
2. 修复多端点路径规范化、真实分叉标记和主干/支路组织；三端点、多 T 点和多目标分别验证。
3. 在共享路由底座落实规则，复验接口单端/双端展开，不能只对两个样例手写坐标或在客户端额外覆盖。
4. 增加线距、共线/接触、分叉 degree 与框边标签检查，并用 playwright-cli/已有 Chromium 分别查看网页、SVG 与 PDF。
5. 根据真实工程规模报告仍需拆图/布局提示的范围，不承诺任意密度全自动。
